一、产品愿景与定位

1.1 产品使命

Focus 要解决的核心问题不是用户没有记录任务，而是用户经常面临：

- 知道自己有很多事情，却不知道应该先做哪件。
- 已有任务清单，但不知道什么时候有时间完成。
- 日程突然变化，需要手动调整大量计划。
- 容易高估自己的时间和精力。
- 专注记录产生了大量数据，却没有真正改善下一次计划。
- 复杂的生产力软件本身占用了太多时间。

Focus 的目标是建立一个可持续自我改善的闭环：

Capture → Plan → Schedule → Focus → Review → Adapt

任务收集 → 计划制定 → 时间安排 → 专注执行 → 结果分析 → 持续优化。

1.2 初期目标用户

优先服务：

1. 大学生与研究生：课程、作业、考试、研究及兼职安排。
2. 独立开发者与创作者：多个项目、不同截止日期、深度工作。
3. 知识工作者：会议、个人任务、专注时间与日常习惯。

先服务个人用户，不急着开发完整的企业项目管理平台。

1.3 产品差异化

Focus 借鉴 Reclaim 的动态时间管理能力、Motion 的任务执行导向，以及优秀日历产品的人性化交互，但不依赖这些产品的私有服务。

Focus 的重点是把计划和实际完成结果联系起来。

例如：

用户安排一个 90 分钟的编程任务 → 实际使用 125 分钟 → Focus 分析同类任务历史 → 逐步改善未来的预计时长 → 在下一次排程时自动留出更合理的时间。

这种能力主要通过统计与程序算法实现。

二、不可改变的产品原则

2.1 Algorithm First, Data Driven, AI Last

Algorithm First

确定性程序负责日程冲突、任务优先级、截止日期、硬约束、版本检查、任务拆分和增量重排。

Data Driven

真实执行记录负责个人耗时估计、偏好学习、工作节奏和排程改善。

AI Last

只有自然语言理解、模糊需求拆解、复杂非结构化资料处理等传统方法难以经济解决的问题，才考虑 AI。

不得让 AI 成为核心数据安全、权限控制或冲突判断的最终裁决者。

2.2 用户始终拥有控制权

- 自动生成的计划可以预览。
- 可以修改、拒绝或锁定任务。
- 不允许静默覆盖手动安排。
- 重要更改可以撤销。
- 计划不可行时必须明确说明。
- 默认不将用户私人日历及行为数据发送给外部 AI。

2.3 审美与体验同等重要

Focus 是产品，不是工程演示。

不能满足于“测试通过、按钮能点击”。

所有主要交互路径必须达到易理解、低操作负担、视觉统一、跨设备可用和无障碍的基本要求。

禁止为了增加视觉效果而无意义地堆积卡片、渐变、阴影与动画。

2.4 低成本和可维护

优先复用现有 Next.js、TypeScript、Supabase、Vercel 和已经运行的测试工具。

没有实际性能或可靠性证据，不新增微服务、独立数据库、消息队列、付费 AI 依赖或复杂 Agent 基础设施。

三、未来产品完整结构

Focus 的长期产品划分为七个相互协作的能力领域。

能力领域| 产品职责| 未来目标
Inbox & Tasks| 收集、整理、分类任务| 低摩擦任务入口
Smart Calendar| 时间规划与动态排程| 自动生成可执行日程
Focus Execution| 专注计时与执行反馈| 计划与真实工作相连
Projects & Goals| 项目、阶段、目标| 支持跨周期目标管理
Personal Intelligence| 统计与个性化学习| 不断改善估时及安排
Review & Insights| 日、周、月回顾| 将数据转化为改进建议
Integrations & Automation| 外部日历、任务工具和 Agent| 减少重复录入及手动协调

这些领域不是要求全部重新开发。

现有功能应继续复用，新能力通过小规模、可测试的增量改进加入。

四、分阶段开发路线

阶段以实际交付和验收门禁推进，不以模型运行时间或固定日期强行宣布完成。

Phase 0 — 工程安全与现有成果集成

对应：Sprint 03 及后续必要的集成工作

优先级：P0

这是目前最重要的阶段。

现有成果包括：

- Focus V1 任务、日历和专注基础
- 409 项 main 基线测试
- Sprint 02 独立排程引擎、后端批量 RPC、前端预览及 QA
- Sprint 03 算法数据适配器与后端计划版本能力的新增 PR

仍须完成：

1. 冻结 Issue #74 的唯一 Smart Calendar 接口契约。
2. 将已开发的算法、数据适配器、后端写入和前端组件安全集成。
3. 验证确认、幂等提交、并发修改与 CAS 撤销。
4. 使用真实 PostgreSQL 双连接测试关键竞争条件。
5. 完成两名测试用户的 RLS 与权限隔离测试。
6. 处理 Issue #55 的迁移历史阻塞。
7. 确认 GitHub CI、Vercel Preview 和生产发布门禁。
8. 对跨分支测试文件和配置变更进行冲突检查。

完成门禁：

- 唯一接口契约得到后端、算法及架构确认。
- 不存在已知 P0 数据丢失、权限泄漏或不可恢复覆盖风险。
- 联合集成 SHA 的所有必要测试通过。
- 可在隔离环境验证计划写入及撤销。
- 不依赖未经授权的生产环境操作。

现阶段未通过这些门禁，不得宣布 Smart Calendar 正式可用。

Phase 1 — Smart Calendar 可用版本

版本目标：Focus 2.0 MVP

优先级：P0

这是 Focus 的第一个关键产品里程碑。

核心能力

- 根据任务、可用时间、截止日期生成日程建议。
- 将固定课程、会议和用户锁定任务视为硬约束。
- 支持任务优先级、缓冲时间和休息间隔。
- 自动保护已接受且仍有效的安排。
- 日程变化时只调整必要任务。
- 在日历上对比原计划与建议计划。
- 清楚展示无法安排的任务及原因。
- 支持手动调整、选择性确认及版本安全撤销。
- 刷新页面后读取真实保存结果。

人性化要求

桌面端采用清晰的时间线和日历交互。

移动端不直接缩小桌面周视图，应采用适合触摸操作的日视图、日期切换和任务详情。

预览必须让用户快速看出：

- 什么任务被移动了？
- 为什么移动？
- 哪些时间不能修改？
- 哪些任务无法安排？
- 点击确认后实际会改变什么？

不包含

第一版不加入复杂机器学习、自动跨平台双向同步、多人协同排程或复杂任务依赖求解。

完成门禁：

用户可以真实完成：

创建任务 → 生成计划 → 查看差异 → 手动修改 → 确认 → 刷新 → 撤销。

全过程通过独立 QA、安全和设计验收。

Phase 2 — 专注执行与计划联动

版本目标：Focus 2.1

优先级：P1

这一阶段要让 Focus 从“会排程”发展为“会协助执行”。

核心能力

1. 从日历任务一键进入专注模式。
2. 自动将专注记录关联到任务和项目。
3. 明确区分开始、暂停、恢复、停止与任务完成。
4. 识别未完成的计划时间块。
5. 当任务超时或中断时建议调整剩余日程。
6. 支持手动延期和剩余时间重新估计。
7. 改善专注完成反馈及每日回顾。
8. 保留用户中断后恢复工作所需的上下文。

产品原则

Focus 不应该通过过度提醒、惩罚式连续打卡或制造焦虑迫使用户工作。

它应该帮助用户了解计划偏差，并提供低压力的恢复路径。

完成门禁：

通过真实用户路径证明计划、执行、记录和后续建议可以正确关联，并且不会重复累计专注时间。

Phase 3 — 个性化生产力引擎

版本目标：Focus 2.2

优先级：P1

这一阶段开始利用真实数据，让每个人的 Focus 逐步形成自己的排程偏好。

个性化维度

A. 实际耗时估计

按任务、项目及活动类型统计历史耗时。

优先采用中位数、加权统计和异常值过滤。

B. 高效时间分析

观察不同时间段的真实专注情况，但不把相关性误认为因果关系。

C. 任务完成表现

记录计划完成率、常见延期、任务重新安排次数和实际用时偏差。

D. 个性化缓冲

根据任务类型、历史估时误差及用户设置，建议合理缓冲时间。

E. 工作节奏

在有足够数据并取得用户认可后，提供专注与休息时间建议。

冷启动机制

新用户没有历史数据时，使用通用默认值和用户主动填写的预计耗时。

数据不足时回退到较保守的估计，不虚构用户偏好。

算法评估

至少与默认估时和简单优先级排程比较：

- 估时平均绝对误差
- 排程覆盖率
- 用户手动修改次数
- 已接受计划扰动程度
- 截止日期满足情况

只有经过真实数据验证有效的改进，才进入默认排程策略。

完成门禁：

在得到授权、数据量充分的试点样本上，证明至少一项个性化指标相对基础策略具有可重复的改善，同时不降低硬约束安全性。

Phase 4 — 外部日历与工具集成

版本目标：Focus 2.3

优先级：P1–P2

目标是让 Focus 能够理解用户在其他系统中的固定安排，而不要求所有信息重新输入一遍。

第一阶段：只读日历连接

优先考虑 Google Calendar。

- 连接账户
- 选择需要读取的日历
- 获取忙闲时间与固定事件
- 正确处理 IANA 时区、重复事件及取消事件
- 将外部占用时段作为排程硬约束
- 对撤销授权和同步失效提供明确反馈

随后根据真实需求考虑 Outlook。

第二阶段：受控写回

经用户明确授权后，再考虑将已确认的 Focus 时间块写入外部日历。

必须防止重复事件、循环同步和误删除原始会议。

第三阶段：任务工具连接

按用户真实需求评估 Todoist、Notion 或其他任务来源。

外部集成必须有实际用户价值，不以集成数量作为产品竞争力指标。

完成门禁：

只读同步可靠、跨用户隔离正确、重复同步不制造重复事件，断开连接后不会破坏 Focus 内部任务。

Phase 5 — 高级计划优化与智能辅助

版本目标：Focus 2.x Advanced

优先级：P2

当基础排程和用户数据达到稳定质量后，逐步研究：

- 大任务自动建议分段安排
- 任务依赖与阶段安排
- 多天、多周的容量规划
- 项目与个人目标之间的时间分配
- 按个人偏好提出替代计划
- 对时间紧张的计划提出可解释的取舍建议
- 更多“假设情况”模拟，例如临时新增会议之后如何调整

复杂算法首先考虑启发式优化、局部搜索与约束求解。

只有数据和实际问题证明必要时，才增加高级求解器。

AI 的角色

AI 可以作为可选辅助层：

1. 将自然语言转成结构化任务。
2. 辅助拆解描述模糊的大型工作。
3. 提取文本资料中的日期和待办。
4. 用自然语言解释统计结果和排程取舍。
5. 为计划提供建议，但不能绕过用户授权和数据库验证。

AI 不负责最终数据库权限判断，也不能绕过硬约束。

没有 AI API 的用户依然可以使用主要生产力功能。

Phase 6 — 产品成熟、开放生态与商业化

版本目标：稳定公开发行及持续运营

优先级：P2–P3

这一阶段不以添加大量新功能为中心，而是提升真实产品质量。

主要工作：

- 完善新用户引导和首次排程体验。
- 优化性能、错误恢复、日志与可观测性。
- 建立数据导出、账号删除和隐私控制流程。
- 完善移动端
